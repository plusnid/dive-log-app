# 要件: UI仕上げ レベル2（テーマカラー・フォント・カードの写真プレビュー）

関連: [設計](./design.md) / [概要](../00-overview.md) / [UI仕上げ レベル1](../ui-polish-level1/requirements.md) / [写真の添付](../photo-attachment/requirements.md) / [モバイル対応](../mobile-compatibility/requirements.md) / [オフライン・PWA](../offline-pwa/requirements.md)

ステータス: 仕様策定中（未着手。配色・フォント・サムネイル方式の[未確定事項](#未確定事項確認したい点)についてユーザー判断待ち）

## 概要

UIデザイン改善の3段階（レベル1〜3）のうち、**レベル2「ダイビングらしさの追加」**を対象とする。
[レベル1](../ui-polish-level1/requirements.md)（情報の強弱・余白・アイコン）で整えた「読みやすさ」の土台の上に、**アプリ固有の世界観（海・水中）**を与えることが目的。

レベル2の内容:

1. テーマカラーを「深い青」に（夜の海・深海をイメージさせる濃いネイビー＋サンゴ色またはターコイズのアクセント）
2. フォントの使い分け（タイトル・見出しに個性を持たせる）
3. 一覧カードに、そのログに添付された写真のサムネイルを小さく表示する

## 用語

- **配色トークン**: `src/index.css` の `:root` に定義するCSSカスタムプロパティ（`--text` / `--bg` / `--surface` / `--border` / `--accent` / `--text-muted`）。
- **アクセントカラー**: 主要な操作（送信ボタン等）と強調表示に使う彩度の高い色。現行は `--accent`（ライト `#0b5b7a` / ダーク `#5fb4d8`）。
- **アクセント上の文字色**: アクセントカラーを背景に敷いたときに、その上に載せる文字の色。現行は `button[type='submit'] { color: #fff }` としてハードコードされている。
- **カードサムネイル**: 一覧のログカード内に表示する、添付写真の縮小画像。
- **表示用サムネイル生成**: 原本のBlobから、表示のために縮小画像を作る処理（DBに保存するかどうかは方式による）。

## 要件（EARS形式）

### 1. テーマカラー（配色トークン）

- REQ-1.1: システムは、アプリの基調色を、深海・夜の海を想起させる濃いネイビーブルー系の色に変更するものとする。
- REQ-1.2: システムは、配色を [ui-polish-level1](../ui-polish-level1/design.md) で定めた既存トークン（`--text` / `--text-muted` / `--bg` / `--surface` / `--border` / `--accent`）の**値の変更**によって実現し、既存トークンの削除・改名を行わないものとする。新たな用途が必要な場合に限り、トークンを追加するものとする。
- REQ-1.3: システムは、ライトモードとダークモードの双方に対して配色を定義し、OSのダークモード設定に追従させるものとする（[mobile-compatibility REQ-6.5](../mobile-compatibility/requirements.md)）。いずれか一方のモードだけを定義した状態や、OS設定を無視して単一配色に固定した状態にはしないものとする。
- REQ-1.4: システムは、ダークモードにおいて、背景（`--bg`）および面（`--surface`）を濃いネイビーブルー系とするものとする。
- REQ-1.5: システムは、ライトモードにおいて、明るい背景（明度の高い面）を維持したうえで、青系の色味を帯びた無彩色に寄せるものとする（ライトモードを暗い配色に反転させないものとする）。
- REQ-1.6: システムは、アクセントカラーとして、サンゴ色またはターコイズブルー系の色を用いるものとする。採用する系統と、両方を使う場合の役割分担は[未確定事項](#未確定事項確認したい点) 2 で確定するものとする。
- REQ-1.7: システムは、アクセントカラーを背景として文字を載せる箇所において、その文字色を配色トークンから参照可能にするものとする（`#fff` のハードコードを解消する）。
- REQ-1.8: システムは、本文・ラベル・データ本体を含むすべての表示テキストについて、その文字色と背景色のコントラスト比を、ライトモード・ダークモードのいずれでも4.5:1以上に保つものとする（[ui-polish-level1 REQ-5.4](../ui-polish-level1/requirements.md) の維持）。
- REQ-1.9: システムは、エラーメッセージ（`.form-error`）の文字色を、新しい配色のライトモード・ダークモード双方でコントラスト比4.5:1以上となる値にするものとする。
- REQ-1.10: システムは、カード・フォーム枠線・入力欄枠線など、面と面を区切る境界を、両モードで視覚的に判別できる明度差を持つ色にするものとする。
- REQ-1.11: システムは、白背景を前提とする描画領域（サインキャンバス `.signature-pad__canvas` / サイン画像 `.detail-signature`）の背景を白のまま維持するものとする（[mobile-compatibility REQ-6.5](../mobile-compatibility/requirements.md) の除外規定）。
- REQ-1.12: システムは、ブラウザUIおよびPWAに通知するテーマ色（`index.html` の `theme-color`、Web App Manifest の `theme_color`）を、変更後の基調色と整合する値に更新するものとする（[offline-pwa REQ-4](../offline-pwa/requirements.md)）。
- REQ-1.13: システムは、既存コンポーネントのCSSに残っているハードコードされた色（`#ccc` / `#f0f0f0` / `#666` 等）のうち、新配色のダークモードでコントラスト比4.5:1（非テキスト要素は3:1）を下回るものを配色トークンに置き換えるものとする。
- REQ-1.14: システムは、配色の変更にあたって外部のCSSフレームワーク・テーマライブラリを新規に導入しないものとする。

### 2. タイポグラフィ（フォント）

- REQ-2.1: システムは、アプリタイトル（「ダイビングログ」）および詳細画面の見出し（ダイビングポイント名）に、本文とは区別できる書式（書体・太さ・字間のいずれか、または組み合わせ）を適用するものとする。
- REQ-2.2: システムは、見出し用と本文用のフォント指定を配色トークンと同じ場所（`src/index.css`）でトークンとして定義し、各コンポーネントからはトークンを参照するものとする。
- REQ-2.3: システムは、フォントの表示のために、実行時に外部ホスト（Google Fonts等のCDN）へのリクエストを発生させないものとする（[概要 NFR-1-b](../00-overview.md)）。
- REQ-2.4: システムは、オフライン状態（初回読み込み後にネットワークを遮断した状態）でも、オンライン時と同一の書体で表示するものとする（[offline-pwa REQ-1](../offline-pwa/requirements.md)）。
- REQ-2.5: フォントファイルをアプリに同梱する場合、システムはそのファイルをService Workerのプリキャッシュ対象に含めるものとする（現行の `workbox.globPatterns` はフォント拡張子を含まないため、対象拡張子の追加を要するものとする）。
- REQ-2.6: フォントファイルをアプリに同梱する場合、システムは再配布が許諾されたライセンス（SIL Open Font License 等）のフォントのみを用い、ライセンス条文と著作権表記をリポジトリに含めるものとする。
- REQ-2.7: フォントファイルをアプリに同梱する場合、システムは初回読み込み時の追加ダウンロード量の増加を、[未確定事項](#未確定事項確認したい点) 3 で合意した上限内に収めるものとする。
- REQ-2.8: 指定した書体が利用できない環境において、システムは代替のシステムフォントで文字を表示し、レイアウトを破綻させないものとする。
- REQ-2.9: システムは、書体・字間の変更後も、日本語（漢字・かな）と半角英数字が混在するテキスト（例: 「城ヶ島・岩骨」「2026-08-09」「20m」）を、文字が重なったり欠けたりせずに表示するものとする。
- REQ-2.10: システムは、入力要素（`input` / `select` / `textarea`）の文字サイズを縮小しないものとする（[ui-polish-level1 REQ-5.3](../ui-polish-level1/requirements.md) の維持。iOS Safari の自動ズーム課題を悪化させないため）。
- REQ-2.11: システムは、フォントの適用のために依存パッケージ（Webフォント配信ライブラリ・サブセット生成ツール等）をビルド時依存として新規に追加しないものとする。追加が避けられない場合は[設計](./design.md)に理由を明記するものとする。

### 3. 一覧カードの写真サムネイル

- REQ-3.1: 一覧のログカードに対応するログが写真を1枚以上持つとき、システムはそのログに添付された写真のサムネイルをカード内に表示するものとする。
- REQ-3.2: システムは、サムネイルに用いる写真を、ログの `photoIds` の**先頭**の写真とするものとする（代表写真の手動選択は行わない）。
- REQ-3.3: システムは、サムネイルを縦横比が一定の領域に収め、元画像の縦横比にかかわらずカードの高さを変動させないものとする（領域からはみ出す部分は切り取って表示するものとする）。
- REQ-3.4: 対応するログが写真を持たないとき、システムはサムネイル領域を表示せず、その分の余白でカードのレイアウトが崩れないようにするものとする。
- REQ-3.5: サムネイルの表示に失敗したとき（実行中のブラウザで表示できない画像形式である場合を含む。[mobile-compatibility REQ-4.5](../mobile-compatibility/requirements.md)）、システムはカードの他の情報の表示を継続し、レイアウトを崩さないものとする。
- REQ-3.6: システムは、サムネイルを装飾として扱い、カードの操作要素としてのアクセシブルな名前（読み上げ内容）を変化させないものとする。写真の有無・枚数はテキスト（メタ行の「写真 N枚」）で伝え続けるものとする。
- REQ-3.7: ユーザーがサムネイルを含むカードのどの位置をタップしても、システムは従来どおり該当ログの詳細画面へ遷移するものとする（[dive-log-crud REQ-1.4](../dive-log-crud/requirements.md)）。サムネイル自体を独立した操作要素（拡大表示等）にはしないものとする。
- REQ-3.8: システムは、一覧のテキスト情報の表示を、写真の読み込み完了を待たずに行うものとする。
- REQ-3.9: システムは、一覧に表示されるすべてのログの写真データを一括して読み込まないものとし、表示に必要となった時点で読み込むものとする。
- REQ-3.10: システムは、サムネイル表示のために生成した一時的なリソース（Object URL 等）を、不要になった時点で解放するものとする。
- REQ-3.11: システムは、写真を添付したログが50件以上ある状態でも、一覧のスクロール操作を継続的に行えること、およびメモリ不足によるタブ／アプリの強制終了を発生させないことを、[mobile-compatibility](../mobile-compatibility/requirements.md) の Tier 1 プラットフォームで満たすものとする。
- REQ-3.12: システムは、サムネイルの表示を端末内のデータのみから行い、ネットワーク接続を要さないものとする（[offline-pwa REQ-1](../offline-pwa/requirements.md)）。
- REQ-3.13: システムは、サムネイル表示のためにUIコンポーネントから Dexie を直接参照せず、リポジトリ層（`src/db/diveLogRepository.ts`）の関数を経由するものとする（[概要のアーキテクチャ](../00-overview.md) の依存の向きを維持）。
- REQ-3.14: ユーザーが写真を追加・削除してログを保存したとき、システムは一覧のサムネイルを再読み込みなしに最新の状態にするものとする（現行の `useLiveQuery` によるリアルタイム反映を維持）。

### 4. 非機能・回帰防止

- REQ-4.1: システムは、本改善によってダイビングログの入力項目・保存される値・詳細画面の表示項目を変更しないものとする。
- REQ-4.2: システムは、本改善によってDexieのスキーマおよび同期対象データ（[google-drive-sync](../google-drive-sync/requirements.md) の `schemaVersion`）を変更しないものとする。サムネイルを永続化する方式を採用する場合に限り、この要件を見直すものとする（[未確定事項](#未確定事項確認したい点) 4）。
- REQ-4.3: システムは、[ui-polish-level1](../ui-polish-level1/requirements.md) で定めた情報の強弱（REQ-1.1〜REQ-1.3）・余白（REQ-2.1〜REQ-2.3）・アイコンの統一（REQ-3.1〜REQ-3.6）を維持するものとする。
- REQ-4.4: システムは、画面幅320px以上の縦向き画面において、横スクロールを発生させないものとする（[mobile-compatibility REQ-6.4](../mobile-compatibility/requirements.md)）。
- REQ-4.5: システムは、操作要素のタップ領域を最小44×44 CSSピクセル以上に保つものとする（[mobile-compatibility REQ-6.3](../mobile-compatibility/requirements.md)）。
- REQ-4.6: システムは、キーボード操作によるフォーカス移動と、フォーカス位置が視覚的に判別できる状態を維持するものとする（[ui-polish-level1 REQ-5.5](../ui-polish-level1/requirements.md)）。
- REQ-4.7: システムは、本改善のために依存パッケージ（UIライブラリ・画像処理ライブラリ・仮想スクロールライブラリ等）を新規に追加しないものとする。追加が避けられない場合は[設計](./design.md)に理由と代替案の検討結果を明記するものとする。
- REQ-4.8: システムは、変更後の配色・書体・サムネイルに関する情報を、リポジトリ公開時に個人を特定できる情報（実際のログ内容・写真等）を含めない形で仕様に記述するものとする。

## 未確定事項（確認したい点）

以下はユーザー判断が必要、または実装前に合意しておきたい点。設計上の推奨案と根拠（コントラスト比の実測値・方式比較）は [設計](./design.md) に記載する。

1. **具体的な配色（HEX値）**: 設計に3案を提示している（[配色候補](./design.md#配色候補3案)）。
   - **案A（推奨）「ダークは深海ネイビー／ライトは白基調＋青み」**: ダーク `--bg #0A1A2F` / `--surface #12263F`、ライトは白い面を維持しつつ `--bg #F2F6FA` に。昼間の屋外（船上・ビーチ）での視認性を落とさない。
   - 案B「両モードとも青を強めに」: ライトの面もごく淡い青（`--surface #FBFDFF` / `--bg #E8EFF6`）にして、明るい時間帯も「海」を感じさせる。
   - 案C「深海テーマに固定（常時ダーク）」: 世界観は最も強いが、OSのダークモード追従（[mobile-compatibility REQ-6.5](../mobile-compatibility/requirements.md)）と矛盾するため、採用する場合は同要件の改訂が必要。**設計としては非推奨**。
2. **アクセントカラー（サンゴ／ターコイズ／両方）**: 現在アクセントが使われているのは「送信ボタンの背景」と「同日引き継ぎ通知の文字色」の2箇所のみ（[洗い出し結果](./design.md#アクセントカラーの現在の適用箇所)）。
   - **案ア（推奨）「ターコイズ1色」**: 浅瀬の水面のイメージで基調のネイビーと同系。落ち着くが変化は控えめ。
   - 案イ「サンゴ1色」: 青の補色で最も鮮やか。ただしライトモードでは白文字とのコントラスト確保のために暗く濁ったサンゴ色（`#C0442E` 前後）になり、「サンゴ」の印象が弱まる。
   - 案ウ「ターコイズ＝主要操作 ／ サンゴ＝強調（同日引き継ぎ通知・写真枚数など）」: 2色運用。トークンが1つ増え、使い分けのルールが必要。
   - どの案でも、アクセント上の文字色は**ライトモードは白／ダークモードは濃紺**になる見込み（明るいターコイズに白文字はコントラスト1.9:1で不可のため）。
3. **フォントの方式**: 設計では**システムフォントスタックの明示と見出し書式の調整（追加ダウンロード0バイト）**を推奨している（[方式比較](./design.md#フォント方式の比較)）。理由は、タイトル・ポイント名がいずれも日本語であり、印象を変えるには日本語グリフを含む書体が必要で、自己ホストすると数MB（サブセット化すればビルド時依存の追加）になるため。
   - 自己ホストを選ぶ場合の候補（いずれもSIL OFL、丸みのある日本語ゴシック）: **Zen Maru Gothic** / **M PLUS Rounded 1c** / **Kiwi Maru**。力強いサンセリフ寄りなら **Noto Sans JP Bold** / **M PLUS 2**。
   - 決めていただきたいのは「自己ホストするか否か」と、するなら「初回ダウンロード増の許容量（例: +500KB まで／+2MB まで）」。**なお、フォントファイルの取得・同梱は本specの範囲外（実装時に別途対応）**。
4. **サムネイルの実装方式**: 設計では**方式1（原本Blobを遅延読み込みして表示、DBスキーマ変更なし）**を推奨し、実機で重い場合に方式2へ移行する判断基準を示している（[方式比較](./design.md#サムネイル方式の比較)）。
   - 方式1: 実装最小・スキーマ変更なし。ただし原本が高解像度（数MB）のままデコードされるため、端末によってはメモリ負荷が読めない。
   - 方式2: 表示時に縮小画像を作ってメモリキャッシュ（原本は即解放）。スキーマ変更なし、初回だけCPUコスト。
   - 方式3: 保存時にサムネイルを生成してIndexedDBへ永続化。最速だがDexieのスキーマ version 3 追加・既存写真のバックフィル・[Google Drive同期](../google-drive-sync/design.md)への影響（同期対象・`schemaVersion`）が発生し、REQ-4.2 の見直しが必要。
5. **サムネイルの枚数とカード内の位置**: 設計では**「先頭1枚をカード右側に64×64で置く」**を推奨（テキストが左、サムネイルが右。写真枚数は既存メタ行の「写真 N枚」で伝える）。
   - 代案: メタ行の下に最大3枚のストリップ（56px×3 ＋「+2」表記）。写真の内容は伝わるがカードが縦に伸び、1画面の表示件数がさらに減る（[ui-polish-level1 の既知のトレードオフ](../ui-polish-level1/design.md#既知のトレードオフ将来への布石)）。
   - 併せて、サムネイル導入後もメタ行の「写真 N枚」を残すかどうか（残す前提で設計している）。
6. **PWAのテーマ色とスプラッシュ**: `theme_color` を新しい基調色に変更すると、ホーム画面から起動したときのステータスバー／タスクスイッチャーの色が変わる。`background_color`（起動時スプラッシュ、現行 `#ffffff`）を濃紺にするかどうかもあわせて判断が必要（濃紺にすると起動時の印象は「深海」に寄るが、ライトモード利用時に一瞬暗い画面が挟まる）。
7. **写真の保存時リサイズ**: 本仕様の対象外としているが、サムネイル表示の負荷とIndexedDB容量の両方に効く根本対策でもある（[photo-attachment の既知の制約](../photo-attachment/design.md#既知の制約)）。別機能として起票するかどうか。

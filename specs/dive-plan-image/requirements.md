# 要件: ダイビングプラン画像の添付

関連: [設計](./design.md) / [概要](../00-overview.md) / [ダイビングログCRUD](../dive-log-crud/requirements.md) / [写真の添付](../photo-attachment/requirements.md) / [写真の拡大表示](../photo-lightbox/requirements.md) / [観察した生物の記録・検索](../marine-life-observation/requirements.md) / [Google Drive同期](../google-drive-sync/requirements.md) / [iOS/Android動作保証](../mobile-compatibility/requirements.md) / [UI仕上げ レベル1](../ui-polish-level1/requirements.md) / [UI仕上げ レベル2](../ui-polish-level2/requirements.md)

ステータス: 仕様確定・実装待ち（[未確定事項](#未確定事項確認したい点) 1〜8 はすべてユーザー確定済み、2026-08-10）。

## 概要

ダイビング前にガイド・ショップから共有される計画図・ルート図・ブリーフィング図等の画像（以下「ダイビングプラン画像」）を、1件のダイビングログに添付できるようにする。**ブリーフィング図が複数ページに分かれる場合に対応するため、1件のログに複数枚を添付できる**（確定事項 2）。

既存の [写真の添付](../photo-attachment/requirements.md) が「そのダイビングで撮った写真」であるのに対し、ダイビングプラン画像は**用途が決まった別の画像群**であり、性質が異なる。したがって本仕様は、写真の一覧に混ぜるのではなく、独立した項目として扱う（データ上は `Attachment.uuid` の配列で指す。確定事項 1）。

表示の拡大には、既存の [写真の拡大表示](../photo-lightbox/requirements.md)（`ImageLightbox`）をそのまま使う。同部品は「対象の集合」が2枚以上のときに前後ナビゲーションと位置表示を出力し、1枚のときは出力しない（[photo-lightbox REQ-3.1, REQ-3.3, REQ-2.5](../photo-lightbox/requirements.md)）。プラン画像の集合をそのまま渡せば、枚数に応じた挙動が自動的に得られるため、部品の変更は不要である。

## スコープ

### 対象

| 対象 | 内容 |
| --- | --- |
| データモデル | ダイビングログにダイビングプラン画像の参照を配列（`Attachment.uuid` の並び）で持つ |
| 入力フォーム | 基本情報の区画でのプラン画像の複数選択・追加・個別の取り除き |
| 詳細画面 | 基本情報の区画での全プラン画像の表示と、選択による拡大表示 |
| 拡大表示 | プラン画像の集合を対象とした拡大表示（2枚以上のときは前後の切り替え） |
| 保存・削除 | 添付の追加・削除の確定、ログ削除時のカスケード削除 |
| Google Drive 同期 | プラン画像の実体と参照（配列）が端末間で運ばれること |

### 対象外（今回やらないこと）

- **プラン画像の編集・注釈・回転・トリミング・共有・ダウンロード**。添付と閲覧のみとする。
- **プラン画像の並び替え（順序の入れ替え）操作**。並びは追加順とする（REQ-1.4）。
- **プラン画像の圧縮・リサイズ**（[photo-attachment/design.md](../photo-attachment/design.md) の既知の制約と同じく、選択したファイルをそのまま保存する）。
- **プラン画像への説明文（キャプション）・ページ番号・作成者・共有元の記録**。
- **プラン画像を対象とした検索・絞り込み**（一覧の検索・フィルタ自体が未実装。[概要の既知の制約](../00-overview.md)）。
- **`ImageLightbox` の機能追加**（ズーム・スワイプ・複数枚のフィルムストリップ等。[photo-lightbox の対象外](../photo-lightbox/requirements.md#対象外今回やらないこと)を維持する）。
- **PDF等、画像以外のファイル形式の添付**（プラン図がPDFで共有される場合は対象外。→ [既知の制約](./design.md#既知の制約トレードオフ)）。
- **同日の直前ログからの引き継ぎ対象への追加**（REQ-2.11）。
- **一覧カードでのプラン画像のサムネイル表示・枚数表示**（一覧カードのサムネイルは引き続き写真から選ぶ。確定事項 8）。

## 用語

- **ダイビングプラン画像**: ダイビング前に共有される計画図・ルート図・ブリーフィング図等の画像。1件のダイビングログにつき0枚以上（REQ-1.3）。本仕様では「プラン画像」と略す。
- **写真**: [photo-attachment](../photo-attachment/requirements.md) が扱う、そのダイビングで撮影した任意枚数の画像。プラン画像とは別の項目として扱う。
- **対象の集合**: 拡大表示で前後に切り替えられる画像の並び（[photo-lightbox 4節](../photo-lightbox/requirements.md)）。

## 要件（EARS形式）

### 1. 項目の定義

- REQ-1.1: システムは、1件のダイビングログに対して複数枚のダイビングプラン画像を添付できるものとする。
- REQ-1.2: システムは、ダイビングプラン画像を任意項目とし、1枚も添付しないままでもフォームの送信を妨げないものとする。
- REQ-1.3: システムは、1件のダイビングログに添付できるダイビングプラン画像の枚数に上限を設けないものとする（写真と同じ扱い。[photo-attachment REQ-1](../photo-attachment/requirements.md)）。
- REQ-1.4: システムは、ダイビングプラン画像の並び順を保持し、入力フォーム・詳細画面・拡大表示のいずれでも同じ順序で扱うものとする。並びは「保存済みの画像（保存された順）→ 当該編集で追加された画像（選択された順）」とし、ユーザーによる並び替え操作は提供しないものとする。
- REQ-1.5: システムは、ダイビングプラン画像を写真（[photo-attachment](../photo-attachment/requirements.md)）とは用途の異なる独立した項目としてユーザーに提示するものとする。ユーザーが写真として追加した画像がプラン画像として扱われること、およびその逆を発生させないものとする。
- REQ-1.6: システムは、ダイビングプラン画像にキャプション・ページ番号・撮影日時・共有元などのメタ情報を保存しないものとする（既存の添付と同じ扱い。[photo-attachment/design.md](../photo-attachment/design.md) の `Attachment`）。
- REQ-1.7: システムは、1つの画像の実体を複数のダイビングログから共有して参照しないものとする（ログごとに独立した添付として保存するものとする）。

### 2. 入力（フォーム）

- REQ-2.1: システムは、入力フォームの基本情報の区画に、ダイビングプラン画像を選択する操作を常時提供するものとする（配置は確定事項 5＝潜水時間の直後）。
- REQ-2.2: システムは、1回の選択操作で複数の画像ファイルを選べるものとする（[photo-attachment REQ-1](../photo-attachment/requirements.md) と同じ）。
- REQ-2.3: ユーザーが画像ファイルを選んだとき、システムはそれらを未保存の候補として**既存の候補に追加**し、それぞれのプレビューを表示するものとする（既に保持している候補・保存済みの画像を置き換えないものとする）。
- REQ-2.4: 編集画面を開いたとき、システムは保存済みのプラン画像を**すべて**プレビューとして表示するものとする（[photo-attachment REQ-3](../photo-attachment/requirements.md) と同じ）。
- REQ-2.5: ユーザーが未保存のプラン画像の取り除きを選択したとき、システムはデータベースに書き込む前にその画像を候補から除外するものとする（[photo-attachment REQ-4](../photo-attachment/requirements.md)）。
- REQ-2.6: ユーザーが保存済みのプラン画像の取り除きを選択したとき、システムはその画像を削除対象としてマークし、フォーム上のプレビューから非表示にするものとする（実削除はフォーム送信時。[photo-attachment REQ-5](../photo-attachment/requirements.md)）。
- REQ-2.7: システムは、プラン画像の取り除き操作を1枚ずつ独立して行えるものとし、他のプラン画像・写真に影響を与えないものとする。
- REQ-2.8: システムは、プラン画像の追加・取り除きをフォームの送信時にまとめて確定するものとする（送信前にデータベースへ書き込まないものとする。[photo-attachment REQ-4〜REQ-6](../photo-attachment/requirements.md) と同じ）。
- REQ-2.9: システムは、プラン画像の選択対象を画像ファイル（`image/*`）に限定するものとする。
- REQ-2.10: システムは、プラン画像の選択で `capture` 属性によるカメラの直接起動を行わないものとする（[photo-attachment REQ-2](../photo-attachment/requirements.md) の方針を踏襲し、複数選択を確実に行えるようにする）。
- REQ-2.11: システムは、同日の直前ログからの引き継ぎ（[dive-log-crud REQ-7.4, REQ-7.5](../dive-log-crud/requirements.md)）の対象にプラン画像を含めないものとする（写真・ガイドサイン画像と同じく、その本固有の値として扱うものとする）。
- REQ-2.12: システムは、プラン画像の追加によって既存の写真添付（`PhotoPicker`）の表示・操作・保存の挙動を変更しないものとする。
- REQ-2.13: ユーザーがフォームを「キャンセル」したとき、システムはプラン画像の変更（追加・取り除きのマーク）を破棄するものとする（[dive-log-crud REQ-2.5](../dive-log-crud/requirements.md)）。
- REQ-2.14: システムは、プラン画像の選択・取り除きの操作要素のタップ領域を最小44×44 CSSピクセル以上とするものとする（[mobile-compatibility REQ-6.3](../mobile-compatibility/requirements.md)）。
- REQ-2.15: システムは、プレビューを生成できない画像について、その旨が分かる代替表示を行い、取り除き操作を維持するものとする（`PhotoPicker` の既存の挙動と同じ）。

### 3. 表示（詳細画面）

- REQ-3.1: システムは、詳細画面の基本情報の区画に、当該ログのダイビングプラン画像を**すべて**表示するものとする（配置は確定事項 5＝基本情報の項目一覧の直後）。
- REQ-3.2: プラン画像が1枚も添付されていないとき、システムは当該表示領域自体を出力しないものとする（画像用の空領域・プレースホルダを表示しないものとする。[ui-polish-level1 REQ-1.7](../ui-polish-level1/requirements.md) の「値が存在する場合のみ表示する」方針に従う）。
- REQ-3.3: システムは、各プラン画像を縦横比を保ったまま、画像全体が見える形で表示するものとする（図の一部を切り取る表示にしないものとする）。
- REQ-3.4: プラン画像が2枚以上あるとき、システムはすべての画像をREQ-1.4の順序で、いずれも初期表示の時点で存在が分かる形で表示するものとする（一部の画像が操作なしには存在を認識できない表示にしないものとする）。
- REQ-3.5: システムは、プラン画像であることが分かるラベル（「ダイビングプラン」）を付けて表示するものとする。
- REQ-3.6: システムは、詳細画面のプラン画像を、写真（「写真・メモ」の一覧）および観察記録のサムネイルと重複して表示しないものとする。
- REQ-3.7: システムは、幅320 CSSピクセル以上の縦向き画面において、プラン画像の表示が画面の横スクロールを発生させないものとする（[mobile-compatibility REQ-6.4](../mobile-compatibility/requirements.md)）。
- REQ-3.8: システムは、解決できない参照（実体が存在しないプラン画像）を表示対象に含めず、その場合もエラーを発生させずに残りの表示を継続するものとする（[marine-life-observation REQ-3.7](../marine-life-observation/requirements.md) と同じ扱い）。

### 4. 拡大表示

- REQ-4.1: システムは、詳細画面の各ダイビングプラン画像を、選択されたときに拡大表示を開く操作要素として提供するものとする（[photo-lightbox REQ-1.1](../photo-lightbox/requirements.md) と同じ方式）。
- REQ-4.2: ユーザーがプラン画像から拡大表示を開いたとき、システムは当該ログのプラン画像全体を、詳細画面での表示順と同じ順序で対象の集合とし、選択された画像を最初に表示するものとする（[photo-lightbox REQ-4.1](../photo-lightbox/requirements.md) と同じ考え方）。
- REQ-4.3: システムは、プラン画像から開いた拡大表示の対象の集合に、写真および観察記録の写真を含めないものとする（[photo-lightbox REQ-4.4](../photo-lightbox/requirements.md) の「開いた箇所から集合を決定する」方針に従う）。
- REQ-4.4: システムは、対象の集合に解決できない画像参照を含めないものとする（[photo-lightbox REQ-4.3](../photo-lightbox/requirements.md)）。
- REQ-4.5: 対象の集合が2枚以上のとき、システムは前後の切り替え操作要素と位置表示（例:「2 / 3」）を提供するものとする。1枚のときはいずれも出力しないものとする（[photo-lightbox REQ-3.1, REQ-3.3, REQ-2.5](../photo-lightbox/requirements.md) の既定の挙動による）。
- REQ-4.6: システムは、拡大表示を開いている間、プラン画像の集合とその並び順を変更しないものとする（[photo-lightbox REQ-3.6](../photo-lightbox/requirements.md)）。
- REQ-4.7: システムは、拡大表示を開く操作要素のアクセシブルな名前および拡大表示中の画像の代替テキストを、対象がダイビングプラン画像であること、および集合が2枚以上のときはその位置が分かる文言とするものとする（[photo-lightbox REQ-7.7, REQ-7.8](../photo-lightbox/requirements.md)。文言は確定事項 6）。
- REQ-4.8: システムは、拡大表示の共通部品（`ImageLightbox`）の公開インターフェースと既存の挙動（閉じる操作・フォーカス管理・背面の不活性化・配色）を変更しないものとする。
- REQ-4.9: 拡大表示に必要なブラウザ機能が利用できない環境において、システムはプラン画像を開く操作要素を提供せず、拡大できない画像として表示を継続するものとする（[photo-lightbox REQ-9.8](../photo-lightbox/requirements.md) と同じ機能検出による分岐）。
- REQ-4.10: システムは、プラン画像の拡大表示のために画像データを再読み込みせず、詳細画面が既に生成している画像URLを再利用するものとする（同一の画像について複数のオブジェクトURLを生成しないものとする。[photo-lightbox REQ-9.5](../photo-lightbox/requirements.md)）。
- REQ-4.11: システムは、拡大表示を開く操作によってダイビングログのデータを読み書きしないものとする（[photo-lightbox REQ-1.7](../photo-lightbox/requirements.md)）。

### 5. 一覧画面

- REQ-5.1: システムは、ダイビングログ一覧のカードにプラン画像の有無・枚数を示す表示を追加しないものとする（確定事項 8）。
- REQ-5.2: システムは、一覧カードに表示する写真の枚数（[dive-log-crud REQ-1.3](../dive-log-crud/requirements.md)）にダイビングプラン画像を含めないものとする（プラン画像が複数枚のときはその全枚数を除くものとする）。
- REQ-5.3: システムは、一覧カードのサムネイル（[ui-polish-level2](../ui-polish-level2/requirements.md) の `CardThumbnail`）にダイビングプラン画像を用いないものとする（写真が1枚以上あるときは写真を用い、写真が0枚のときはサムネイルを表示しないものとする）。

### 6. 保存・削除・ライフサイクル

- REQ-6.1: ユーザーがフォームを送信したとき、システムは新規に選択されたプラン画像をすべて保存し、削除マークの付いたプラン画像をすべて削除し、ログのプラン画像の参照（配列）を最新の状態に更新するものとする（[photo-attachment REQ-6](../photo-attachment/requirements.md) と同じ形）。
- REQ-6.2: ユーザーがプラン画像を取り除いたうえでフォームを送信したとき、システムは当該画像の実体を削除するものとする（参照されない添付を残さないものとする）。
- REQ-6.3: ダイビングログが削除されたとき、システムは紐づくプラン画像もすべて削除するものとする（[dive-log-crud REQ-5.2](../dive-log-crud/requirements.md) のカスケード削除に含めるものとする）。
- REQ-6.4: システムは、プラン画像の削除時に同期用の墓標（tombstone）を、写真・サイン画像と同じ方式で記録するものとする（[google-drive-sync](../google-drive-sync/requirements.md)）。
- REQ-6.5: システムは、保存時にプラン画像の参照配列から、実体が存在しない参照および重複した参照を取り除くものとする（[marine-life-observation REQ-3.6, REQ-3.7](../marine-life-observation/requirements.md) の観察記録の写真参照と同じサニタイズ方針）。
- REQ-6.6: 端末のストレージ容量不足により保存に失敗したとき、システムは既存と同じエラー表示を行い、ログの内容を破壊しないものとする（[mobile-compatibility](../mobile-compatibility/requirements.md) の容量不足時の挙動を変更しないものとする）。

### 7. 既存データとの互換性

- REQ-7.1: プラン画像を持たない既存ログについて、システムは0枚として扱い、表示・編集・保存を妨げないものとする（データ移行・バックフィルを行わないものとする。[dive-log-crud REQ-4.4, REQ-4.5](../dive-log-crud/requirements.md) と同じ方針）。
- REQ-7.2: システムは、本機能の追加によって既存の写真・ガイドサイン・観察記録の保存内容および表示内容を変更しないものとする。
- REQ-7.3: システムは、観察記録（[marine-life-observation REQ-3.1](../marine-life-observation/requirements.md)）に紐づけられる写真の選択候補にダイビングプラン画像を含めないものとする。

### 8. Google Drive 同期

- REQ-8.1: 同期が有効なとき、システムはダイビングプラン画像の実体と参照（配列）を端末間で運ぶものとする（一方の端末で添付したプラン画像が、他方の端末でも同じログのプラン画像として、同じ枚数・同じ順序で表示されるものとする）。
- REQ-8.2: システムは、本機能の追加によって同期の `schemaVersion`、Drive上のファイル構成、およびログファイルのトップレベルの構造を変更しないものとする（プラン画像の参照はログ本体の項目として運ばれるものとする）。
- REQ-8.3: システムは、競合コピーを作成するとき、プラン画像の参照配列の各要素を複製後の画像へ付け替えるものとする（[marine-life-observation REQ-8.4](../marine-life-observation/requirements.md) と同じ扱い）。複製できなかった参照は落とすものとし、残りの参照と順序を保つものとする。
- REQ-8.4: システムは、本機能を持たないバージョンのアプリが動作する端末との間でデータをやり取りしても、プラン画像の参照および実体を失わせないものとする。
- REQ-8.5: システムは、競合解決の粒度をログ単位のまま変更しないものとする（[google-drive-sync REQ-6](../google-drive-sync/requirements.md)）。

### 9. 非機能・回帰防止

- REQ-9.1: システムは、本機能の実装のために依存パッケージを新規に追加しないものとする。
- REQ-9.2: システムは、プラン画像の添付・表示・拡大表示をオフラインで動作可能とするものとする（[概要 NFR-1, NFR-2](../00-overview.md)）。
- REQ-9.3: システムは、本機能の追加によって Dexie の `stores()` 定義およびデータベースのバージョンを変更しないものとする（非キー項目の追加のみで済ませる方針とする。[dive-log-crud/design.md](../dive-log-crud/design.md) / [marine-life-observation/design.md 4](../marine-life-observation/design.md) と同じ判断）。
- REQ-9.4: システムは、UIコンポーネントから Dexie を直接操作せず、リポジトリ関数を経由する既存の依存の向き（[概要のアーキテクチャ概要](../00-overview.md)）を維持するものとする。
- REQ-9.5: システムは、本機能で追加する配色・アイコンを既存の方式（配色トークン／インラインSVG・単色・文字色追従・支援技術から除外）で実装するものとする（[ui-polish-level1 REQ-3.2〜REQ-3.5](../ui-polish-level1/requirements.md), [ui-polish-level2](../ui-polish-level2/requirements.md)）。外部のアイコンライブラリ・Webフォント・外部ホストの画像を導入しないものとする。
- REQ-9.6: システムは、プラン画像の圧縮・リサイズ・形式変換を行わず、選択されたファイルをそのまま保存するものとする。
- REQ-9.7: システムは、プラン画像のプレビュー・表示・拡大表示の繰り返しによって、解放されないオブジェクトURLが残らないものとする（複数枚を扱う場合も、生成したすべてのURLを解放するものとする。[photo-lightbox REQ-9.6](../photo-lightbox/requirements.md)）。
- REQ-9.8: システムは、本仕様およびコードに、公開リポジトリで問題となる個人情報・機密情報を含めないものとする（例示には一般的な記述のみを用いるものとする）。

## 未確定事項（確認したい点）

すべてユーザー確定済み（2026-08-10）。各項目の比較・根拠は [設計](./design.md) の該当節を参照。

1. **データの持ち方**（REQ-1.5, REQ-8.2, REQ-8.4, REQ-9.3。[設計 1](./design.md#1-データの持ち方)）: **確定＝案B（写真と同じ `attachments` に保存して `photoIds` にも含め、どれがプラン画像かをログ側の `Attachment.uuid` 参照で指す）**。ただし確定事項 2 により参照は単数ではなく**配列**（`DiveLog.planImageUuids?: string[]`）とする。観察記録が写真を `Attachment.uuid` で指すのと同じ方式（[marine-life-observation/design.md 2](../marine-life-observation/design.md)）であり、同期エンジン・Driveのファイル形式・`schemaVersion` は無変更で、旧バージョン端末との混在でも値が保持される。代わりに、写真の枚数・一覧カードのサムネイル・観察記録の写真候補から「プラン画像を除外する」処理が表示側・リポジトリ層に必要になる（[設計 6](./design.md#6-リポジトリ層srcdbdivelogrepositoryts), [設計 8](./design.md#8-一覧カードへの表示)）。不採用: 案A（`type: 'plan'` の専用添付。同期エンジンの改修と旧版端末経由でのデータ喪失リスクを伴う）、案C（同期対象外のローカル専用データ）。

2. **枚数**（REQ-1.3, REQ-1.4。[設計 2](./design.md#2-枚数)）: **確定＝複数枚を許容し、上限を設けない**。ブリーフィング図が複数ページに分かれる場合に対応するため。当初の推奨案（1枚固定）は不採用。並び替え操作は提供せず、並びは追加順とする。

3. **入力UI**（REQ-2.1〜REQ-2.10。[設計 3](./design.md#3-入力uiplanimagepicker)）: **確定＝プラン画像専用の新規部品 `PlanImagePicker` を作る**。既存の `PhotoPicker` は変更しない（REQ-2.12）。ただし確定事項 2 により、複数選択・複数プレビュー・個別の取り除き（保存済み／未保存の2系統）という `PhotoPicker` と同等の機能を持たせる。専用部品にする理由は、プレビューの見せ方（切り取らずに全体を見せる）とラベル・代替テキストがプラン画像固有であり、写真添付という中核機能に分岐を持ち込まないためである。カメラの直接起動（`capture`）は付けない（REQ-2.10）。

4. **必須／任意**（REQ-1.2）: **確定＝任意項目**。既存の写真・サインと同じ扱い。

5. **配置**（REQ-2.1, REQ-3.1。[設計 4](./design.md#4-配置)）: **確定＝フォームは基本情報 `fieldset` の末尾（潜水時間の直後）、詳細画面は基本情報 `section` の `<dl>` の直後**。独立したセクションは設けない。

6. **詳細画面での表示方法**（REQ-3.3〜REQ-3.5, REQ-4.7。[設計 5](./design.md#5-詳細画面での表示とライトボックス連携)）: **確定＝1枚あたり横幅いっぱい・最大高さ240px・`object-fit: contain`（全体表示）**。ラベルは「**ダイビングプラン**」、拡大表示の代替テキストの主部は「**ダイビングプランの画像**」とし、2枚以上のときは `ImageLightbox` が位置（「1枚目 / 全2枚」）を自動的に付加する。**複数枚の並べ方は縦積み（1列）とする**（[設計 5-1](./design.md#5-1-複数枚のレイアウト)で横スクロールのストリップ・2列グリッドと比較のうえ決定）。

7. **同期への影響**（REQ-8.1〜REQ-8.5。[設計 7](./design.md#7-google-drive-同期への影響)）: **確定＝同期エンジン（`src/sync/`）・Driveのファイル形式・`schemaVersion` はいずれも無変更**。必要な変更は競合コピー時の参照の付け替え（`src/db/syncRepository.ts` の `createConflictCopy()`）のみで、配列の各要素を写像する処理になる。

8. **一覧カードへの表示**（REQ-5.1）: **確定＝追加しない**。ただし案Bの帰結として、写真枚数からプラン画像の枚数を除く（REQ-5.2）およびサムネイルにプラン画像を用いない（REQ-5.3）の2点の手当ては必須である（[設計 8](./design.md#8-一覧カードへの表示)）。
